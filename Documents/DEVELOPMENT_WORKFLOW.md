# 開発・ブランチ運用

この文書は、ゲーム仕様を実装する前のリポジトリ運用ルールを定める。ゲームの挙動に関する規範は各仕様書を参照する。

## 1. ブランチ

- `main` は共有する基準ブランチとし、常にレビュー可能な状態に保つ。
- 作業は `main` の最新状態から短命なブランチを作って行う。`main` への直接コミットはしない。
- ブランチ名は目的が分かる英小文字の接頭辞と説明を使う。
  - `docs/` — 仕様書・開発文書
  - `feature/` — ゲーム機能
  - `fix/` — 不具合修正
  - `chore/` — 設定・依存関係・保守作業
  - 例: `docs/branch-workflow`, `chore/godot-gitignore`
- 作業ブランチは目的ごとに分け、完了後はレビューを経て `main` に取り込む。取り込み後のブランチ削除は任意。

## 2. 変更とレビュー

- Pull Request（または同等のレビュー）には、目的、主な変更、確認内容、未解決事項を記載する。
- 仕様変更と実装変更は可能なら分ける。実装が仕様に依存する場合は、先に仕様の合意状態を明確にする。
- レビューでは仕様との整合性、既存挙動への影響、受け入れ条件を確認する。未決定事項を暗黙に確定しない。
- 自動チェックが設定されている場合は、取り込み前に成功を確認する。チェックがない場合は、実施していない確認を成功扱いにしない。
- コミットメッセージは変更の目的が分かる短い要約にする。例: `docs: add branch workflow`、`chore: ignore Godot cache`。

## 3. 仕様書の優先順位

- `SQUAD_BEHAVIOR.md` は命令・小隊・交戦状態、`MOVEMENT_SPEC.md` は移動と経路、`INPUT_SPEC.md` は操作の規範を定める。
- `UI_DESIGN.md` は戦闘画面の情報と見た目の暫定仕様を定める。暫定値は調整可能な案として扱い、命令や入力動作と衝突する場合は規範仕様に合わせるか、判断を確認する。
- `EQUIPMENT_DATA_MODEL.md` はMATE本体・装備・編成の暫定データ項目を定める。未決の戦闘処理・編成制約は実装で確定せず、表示用サンプル値はゲームバランスとして扱わない。
- `ACCEPTANCE_TESTS.md` は合意済み挙動の具体的な受け入れ条件を記録する。暫定項目は仕様の確定前に必須条件として扱わない。
- `GAME_DESIGN.md` は企画全体と資料群の案内を担う。個別の規範仕様と矛盾する場合、個別仕様を優先する。
- 文書間の矛盾や未記載事項は、担当する仕様書に判断を記録し、関連する受け入れ条件も必要に応じて更新する。判断が済むまでは推測で埋めない。
- 各文書の状態表記（合意・確定・提案・仮案・未決）を維持し、変更時は関連文書の状態と版情報を揃える。

## 4. リポジトリに含めるもの

- 追跡対象は、Godotプロジェクト設定、ゲームのソース・アセット、仕様書、開発に必要な共有設定とする。
- Godotの `.godot/` キャッシュ、エクスポート出力、OSの一時ファイルや個人用ショートカットはコミットしない。
- インポート設定（例: `*.import`）や共有プロジェクト設定は、再現に必要な場合があるため、生成物と決めつけて除外しない。
- 秘密情報、個人の環境設定、再生成可能な大容量成果物を追加しない。必要な共有データは用途と生成方法を文書化する。

## 5. 変更記録

仕様変更では、変更理由と影響する受け入れ条件をPull Requestまたは変更履歴に記録する。数値やゲームルールを決定する場合は、決定済みであることを明記し、草案の提案と区別する。
